# Plan de diseño y ejecución UI v1.3

Estado: listo para iniciar concepto visual

Fecha: 2026-08-28

Rama base: `feature/v1.3.0-ui-foundation`, creada desde `main` después de
publicar v1.2.0 y completar la limpieza de ramas.

## Decisión

WizZ Desktop conservará Flet, Python y el controlador LAN actual. El rediseño
adoptará el proceso de la skill `frontend-app-builder`: concepto visual
completo antes de programar, sistema de diseño derivado del concepto,
implementación incremental y comparación visual estricta.

La skill se adapta a una aplicación nativa de escritorio:

- Flet sustituye a React/Vite porque es el framework existente y probado;
- ImageGen se usa para mockups de diseño, nunca como interfaz final;
- todos los textos, controles, iconos y estados continúan siendo código Flet;
- la validación rápida puede usar una vista Flet web cuando resulte útil, pero
  la aceptación final se realiza en builds nativas de Windows y Linux;
- los conceptos aprobados se guardan como evidencia de diseño, no como assets
  cargados por la aplicación.

## Objetivo de producto

Crear una interfaz elegante, minimalista, fluida y fácil de entender que:

- muestre la selección de luces desde el inicio;
- permita seleccionar una, varias o todas sin editar grupos permanentes;
- responda visualmente en el mismo clic;
- mantenga las acciones principales a uno o dos pasos;
- sea consistente en Windows y Linux;
- se adapte a ventanas compactas, regulares y amplias;
- evite refrescos, animaciones o repaints innecesarios;
- conserve el control LAN, persistencia y estabilidad de v1.2.0.

## Límites de esta fase

No se incluye:

- migración a C++, Qt, React u otro motor;
- Quick Panel o ventanas flotantes temporales;
- soporte RGBIC público;
- Screen Sync, streaming o Effects Engine productivo;
- cambios al protocolo WiZ, discovery, formatos JSON o rutas de datos;
- instalación automática de actualizaciones.

## Principios visuales

1. Una tarea dominante por pantalla.
2. Menos contenedores anidados y menos tarjetas decorativas.
3. Jerarquía tipográfica clara antes que bordes, brillos o gradientes.
4. Estados selected, hover, focus, pressed, disabled, loading, offline y mixed
   visibles sin depender únicamente del color.
5. Iconos coherentes en metáfora, tamaño, peso y alineación.
6. Espaciado generoso, pero con controles importantes visibles en una ventana
   de notebook sin scroll inicial innecesario.
7. Movimiento corto y funcional; nada debe retrasar el comando enviado.
8. Contraste y foco de teclado revisados en ambos idiomas.

## Fase 0 — línea base verificable

Antes de cambiar componentes se registrará:

- captura nativa actual de Home, Color Studio, Scenes, Favorites, Routines y
  Settings en Windows;
- capturas equivalentes de Home, Color Studio y estado Hotkeys no disponible
  en Ubuntu;
- tamaños de ventana compacta, regular y amplia;
- tiempo de inicio, memoria e idle CPU de una build empaquetada;
- lista de controles Flet deprecados y estilos duplicados;
- flujos funcionales y textos visibles que no pueden desaparecer.

No se fijarán promesas numéricas de rendimiento hasta medir esta línea base.

## Fase 1 — conceptos visuales con ImageGen

Se crearán mockups coordinados, legibles y completos para:

1. **Home regular (1080 × 720):** navegación, estado general, selector rápido
   multi-luz, control maestro, brillo y accesos realmente útiles.
2. **Home compacto:** mismo flujo sin contenido cortado ni navegación confusa.
3. **Color Studio regular:** picker, blanco Kelvin, preview, controles precisos
   y acción live/manual con menor densidad visual.
4. **Biblioteca:** lenguaje compartido para Scenes y Favorites, incluyendo
   estados vacío, seleccionado y dispositivo incompatible.
5. **Settings/Linux:** estado de integración de escritorio y Hotkeys no
   disponibles con explicación clara.

Restricciones del prompt visual:

- conservar la arquitectura de información y nombres reales del producto;
- no inventar métricas, funciones, dispositivos o servicios en la nube;
- no incluir Quick Panel ni RGBIC;
- evitar grids genéricos de tarjetas, glassmorphism excesivo y decoración sin
  función;
- mantener controles implementables con Flet 0.85.x;
- producir textos suficientemente legibles para extraer medidas y jerarquía.

### Gate de aprobación visual

No se modifica la UI productiva hasta que el usuario apruebe:

- dirección de color y superficies;
- navegación y densidad;
- anatomía del selector de luces;
- organización de Home y Color Studio;
- comportamiento compacto;
- nivel de animación.

Una vez aprobado, el concepto se considera especificación. Cualquier cambio
visible posterior debe compararse contra él o documentarse como desviación.

## Fase 2 — sistema de diseño Flet

Extraer del concepto aprobado:

- paleta semántica: background, surface, raised, border, text, muted, accent,
  success, warning, error y disabled;
- escala de espaciado y tamaños mínimos interactivos;
- tipografía de títulos, cuerpo, etiquetas, controles y datos;
- radios, bordes, elevación y tiempos de movimiento;
- tratamiento de iconos y navegación;
- breakpoints compact, regular y wide basados en el panel útil real.

Entregables previstos:

- ampliar `ui/theme.py` sin romper sus consumidores actuales;
- consolidar primitivas en un módulo pequeño de componentes compartidos;
- reemplazar gradualmente estilos inline y `ft.ElevatedButton` deprecados;
- añadir pruebas para variantes, estados y breakpoints.

No se realizará un reemplazo mecánico global de estilos.

## Fase 3 — implementación por cortes verticales

### 3.1 Shell y navegación

- navegación clara en regular/wide y alternativa compacta;
- título, destino activo y estado online sin competir por atención;
- navegación Hotkeys deshabilitada de verdad en Linux, con tooltip explicativo;
- foco de teclado visible y orden lógico.

### 3.2 Home y targeting

- selector visible antes de los controles;
- click con feedback inmediato, independiente del polling de estado;
- estados single, selected y all inequívocos;
- resumen de cantidad, online/offline y capacidades mixtas;
- acciones rápidas limitadas a las de mayor uso;
- pruebas con `WIZZ_DEV_VIRTUAL_BULBS` y la luz real disponible.

### 3.3 Color Studio

- separar claramente RGB y blancos Kelvin;
- reducir contenedores y jerarquía redundante;
- mantener preview, live/manual, valores precisos, recientes y favoritos;
- coalescer sliders sin retrasar botones directos;
- verificar que seleccionar otra luz nunca fuerce un frame de escena.

### 3.4 Scenes y Favorites

- biblioteca visual compartida con filtros simples;
- disponibilidad y capacidades visibles;
- aplicación rápida y edición secundaria;
- estados vacío, loading, error e incompatibilidad.

### 3.5 Routines y Settings

- editor por pasos fácil de escanear;
- configuración agrupada por intención, no por detalles técnicos;
- Datos, Logs, actualizaciones e integración de escritorio visibles;
- textos específicos de Windows/Linux según la plataforma real.

## Fase 4 — rendimiento y refresco adaptable

- separar estado de selección, estado de luz y estado visual transitorio;
- actualizar únicamente controles afectados;
- coalescer input continuo y mantener acciones discretas inmediatas;
- polling bajo en idle y acotado durante interacción activa;
- suspender trabajo visual cuando la ventana está oculta;
- respetar movimiento reducido cuando la plataforma lo permita;
- comparar cada medición contra la línea base de Fase 0.

## Fase 5 — verificación visual y funcional

Para cada pantalla migrada:

1. captura del concepto aprobado;
2. captura de la implementación en el mismo tamaño;
3. inspección lado a lado de layout, textos, tipografía, color, iconos,
   espaciado, estados y responsive;
4. registro de diferencias corregidas o desviaciones aceptadas;
5. prueba del flujo interactivo real.

Matriz final:

- Windows y Ubuntu;
- español e inglés;
- compact, regular y wide;
- cero, una y múltiples luces virtuales;
- una luz WiZ real;
- online, offline, mixed capabilities y loading;
- mouse y teclado;
- aplicación desde código fuente y build empaquetada.

Validación automatizada mínima por corte:

```text
python -m pytest -q
python -m compileall -q main.py app_meta.py core config ui localization tests tools
python tools/i18n_audit.py
git diff --check
```

## Estrategia Git

- `main` permanece publicable;
- el trabajo se realiza en `feature/v1.3.0-ui-foundation`;
- commits pequeños por concepto, tokens y pantalla;
- no mezclar RGBIC, Quick Panel o cambios de protocolo;
- PR parcial solo cuando el corte mantiene pruebas y flujos existentes;
- preservar capturas y decisiones relevantes en `docs/codex/`.

## Definición de terminado

- conceptos completos aprobados antes de implementar;
- sistema visual consistente y reutilizable;
- targeting inmediato y comprensible;
- Home y Color Studio sin cortes en tamaños soportados;
- ninguna función pública de v1.2.0 desaparece;
- sin controles Flet deprecados en las pantallas migradas;
- traducciones, foco, disabled y contraste verificados;
- regresión funcional completa en Windows/Linux;
- rendimiento empaquetado igual o mejor que la línea base medida;
- comparación visual final sin diferencias materiales pendientes.
