# WizZ Desktop v1.2 public release and RGBIC closed beta roadmap

Status: In Progress

Date: 2026-08-27

Branch at planning baseline: `release/v1.2.0-windows`

Baseline commit: `f158d30`

## 1. Objective

Deliver the next version through two intentionally separate channels:

1. a stable public Windows release plus a clearly labelled Linux beta focused
   on reliable everyday control; and
2. a closed RGBIC beta for controlled validation with the community hardware
   tester.

The work must preserve the functioning WiZ control path, avoid broad UI or
platform rewrites during release stabilization, and keep experimental RGBIC
behavior out of the public stable channel.

## 2. Product outcomes

### Public channel: WizZ Desktop v1.2.0

The public release should provide:

- stable Windows operation for existing v1.1.0 users;
- quick transient selection of one, several or all saved lights;
- persistent user configuration outside the installed/build directory;
- reliable main-window, tray, hotkey and current Quick Panel behavior;
- a polished Home targeting experience with clear single, selected and all
  states;
- read-only update availability checking and a safe route to the GitHub
  release page;
- a reproducible Windows artifact, checksum and release checklist.

### Closed channel: RGBIC beta

The beta should provide only the minimum surface required to validate the
existing experimental RGBIC foundation:

- an explicit beta/prerelease version and artifact;
- manual calibration input for the tester's installation;
- explicit scene slot input, never a hardcoded universal `sceneId`;
- one-shot experimental sends through the approved `LightController` bridge;
- sanitized fixture/report generation;
- visible warnings that transport success is not visual confirmation;
- no scheduler, streaming, Screen Sync or public support claim.

## 3. Scope boundaries

### Included in the v1.2.0 public release

- Windows stable runtime and packaging.
- Linux beta runtime, packaging and Ubuntu Desktop validation. Linux is part
  of the same v1.2.0 release only after its dedicated beta gate passes.
- Transient multi-target selection already implemented in commit `93c0136`.
- Packaged Windows persistence uses `%LOCALAPPDATA%\\WizZDesktop`; a Flet
  Documents-based legacy location is migrated on first launch.
- Read-only GitHub release discovery already implemented in commit `2b3bd9b`.
- Targeted Home UI improvements needed to expose and explain selection.
- Deprecation cleanup only where it is small, mechanical and covered by tests.
- Documentation, version metadata, changelog, build artifact and smoke tests.

### Explicitly excluded from v1.2.0

- Production RGBIC support.
- Effects scheduler, realtime session, streaming or Screen Sync.
- Automatic download, replacement or restart of the executable.
- A new installer technology or signing pipeline.
- The independent Quick Panel native-window redesign.
- A UI-engine migration or PySide6/C++ rewrite.
- macOS implementation, CI or support claims.
- Refactors of `LightController`, `WizProtocol`, action sequences or persisted
  favorites that are unrelated to a demonstrated release defect.

### Deferred design work

The separate temporary Quick Panel window remains an approved *future* design
in `docs/codex/queries/2026-08-27-02-quick-panel-window-redesign.md`. It is
not a v1.2.0 release gate: after real geometry and focus failures, the active
v1.2.0 composition no longer creates a Quick Panel. The tray restores only the
main window until an independent implementation is manually validated.

## 6. Phase B — Home multi-target UX stabilization

Status: Completed on 2026-08-27. The deterministic controller/component
contracts are covered by tests. A DEV-only virtual multi-light fixture was
also added for manual source-run testing; its continuous scene-frame delivery
is not release evidence because Flet desktop repaint timing remains irregular.

### User interaction contract

- The destination selector is visible near the top of Home.
- One click toggles a light in or out of the transient selection.
- At least one light remains selected when saved lights exist.
- Selecting every light maps to `all`.
- Selecting one light maps to `single`.
- Selecting two or more, but not all, maps to `selected`.
- The UI communicates how many lights will receive the next action.
- Selection does not require creating, naming or editing a permanent group.
- Existing controls continue to call the same `LightController`.

### States to design and test

- no saved lights;
- one saved light;
- multiple saved lights, one selected;
- multiple saved lights, partial subset selected;
- all saved lights selected;
- selected light offline or removed;
- discovery refresh while a selection exists;
- narrow and normal desktop window widths;
- Spanish and English labels.

### Tests and evidence

- Pure/controller tests simulate at least three bulbs.
- Component tests verify selection toggling and state labels.
- Existing `tests/test_target_selection.py` remains green.
- Hardware smoke uses the available single bulb for command correctness.
- A future community/multi-device tester validates a real partial subset; this
  is desirable evidence but not a blocker when simulated contracts pass.

### Exit gate

- No command is sent to a target outside the selected set in tests.
- Single and all behavior remains backward compatible.
- Home remains usable at the supported minimum window size.

## 7. Phase C — Safe update notification

Status: Completed on 2026-08-28. The Settings UI provides an explicit,
background, read-only stable-channel check and only opens the validated
official release page. No download or installation path was added.

### v1.2.0 behavior

- Query GitHub Releases only on explicit user action or a bounded background
  check after startup.
- Compare the running version with the selected release channel.
- Stable users ignore prereleases.
- Beta users may opt into prereleases in a later beta-only setting.
- Show current version, available version and release notes link.
- Open the official GitHub release page using the platform integration
  boundary.
- Network failure, timeout, malformed JSON or GitHub rate limiting must not
  prevent WizZ from starting or controlling lights.

### Not yet authorized

- Silent background downloads.
- Replacing a running executable.
- Elevation prompts.
- Installer self-update.
- Automatic rollback.

GitHub Releases is sufficient free hosting for the version metadata and
downloadable artifacts. Automatic installation remains a later phase after
the installer, integrity and rollback model are designed.

### Exit gate

- Update checks are read-only and failure-safe.
- Stable/prerelease channel tests remain deterministic without network access.
- The UI contains no hardcoded visible strings.

## 8. Phase D — Windows release hardening

Status: Completed on 2026-08-28.

### Automated validation

Run from the project virtual environment:

```powershell
python -m pytest -q
python -m compileall -q main.py app_meta.py core config ui localization tests tools
python tools/i18n_audit.py
python tools/desktop_selftest.py
git diff --check
```

### Manual Windows smoke matrix

- clean start with no existing process;
- second-instance activation;
- discovery and manual light persistence;
- one-light power, brightness, RGB, Kelvin and scene control;
- Home selection states;
- tray open, hide, restore and real exit;
- global hotkey registration and execution;
- no Quick Panel activation; the tray must restore only the main window;
- settings and favorites persistence after restart;
- packaged build reads the existing per-user configuration;
- rebuilding/replacing the application does not erase configuration;
- no real config JSON, IP, MAC, hotkey or log is packaged in the artifact.

### Packaging validation

- Build with `flet build windows` and the project release script.
- Inspect the generated `BUILD_INFO.json`.
- Verify the ZIP filename/version and SHA-256 file.
- Launch the extracted artifact outside the repository.
- Confirm configuration remains in `%LOCALAPPDATA%\\WizZDesktop`.
- Confirm third-party notices and required assets are present.

### Exit gate

- Automated suite and GitHub workflows are green.
- Manual smoke matrix has no release-blocking failure.
- Known Flet deprecation warnings are documented and do not hide new warnings.

### Linux beta gate added on 2026-08-28

- The packaged app starts on Ubuntu Desktop using native Flet Linux output.
- Shared controls, discovery and local WiZ control pass a real LAN smoke test.
- GNOME/Wayland tray uses AppIndicator when available; if unavailable, the app
  remains usable with normal window close behavior and an explicit capability
  report.
- Settings opens data/log folders through `xdg-open` and manages a user XDG
  autostart entry.
- The build stores configuration under the packaged Flet/XDG user storage,
  never under the installed artifact directory.
- Global hotkeys, exact window placement and second-instance foreground
  activation are documented as desktop/compositor-dependent beta limitations.
- A Linux archive and SHA-256 are produced from the same approved v1.2.0
  release commit as the refreshed Windows archive.

### Definition of done

- The public artifact launches and controls a real WiZ bulb.
- Existing per-user data survives replacement of the application directory.
- The release page and checksum are available.
- `main`, the tag and both platform artifacts identify the same version.
- Stable update checks select `v1.2.0` and ignore RGBIC prereleases.

## 10. RGBIC closed beta after v1.2.0

### Branch and channel

- Create `beta/v1.3.0-rgbic` from the approved `v1.2.0` tag.
- Integrate reviewed RGBIC foundation changes through explicit commits or a
  PR; do not merge an unknown historical branch wholesale.
- Use a prerelease version such as `v1.3.0-beta.1`.
- Publish it as a GitHub prerelease or distribute the artifact only to the
  named tester.
- Stable channel selection must ignore this prerelease.

### Beta validation order

1. Re-run pure model, compression, mapping, encoder and fixture tests.
2. Confirm `physical_segments=17` for the tester's current installation.
3. Require manual `sceneId` input and record firmware/model metadata.
4. Send one controlled pattern through the existing experimental bridge.
5. Ask the tester for visual confirmation separately from transport success.
6. Generate and review a sanitized artifact before it is returned or shared.
7. Compare an alternate slot only when the protocol procedure calls for it.
8. Stop after the planned slot/pattern; no automatic sequence or streaming.

### Beta stop conditions

- unexpected device state or saved-scene activation;
- firmware/model mismatch not represented in the fixture;
- payload rejection or inconsistent visual result;
- any need to hardcode a universal `sceneId`;
- any request to bypass `LightController` or open a second UDP path;
- any artifact containing tester IP, MAC or other unsanitized identifiers.

### Promotion criteria

RGBIC remains beta until multiple fixtures and firmware/device combinations
support a stable capability, calibration and slot-selection policy. One
successful tester session is evidence, not a production support guarantee.

## 11. Linux beta implementation

Linux is now an in-progress v1.2.0 workstream on `feature/v1.2.0-linux-beta`:

- preserve the validated platform contracts and fakes;
- select the compatible AppIndicator tray backend before pystray is imported;
- wire XDG autostart and `xdg-open` through the existing platform boundary;
- degrade hotkeys honestly on Wayland when permissions/backend are absent;
- retain Unix single-instance exclusion while documenting that foreground
  activation is not yet portable;
- create a Linux package only after tray, window and persistence behavior are
  tested as an installed application.

macOS stays deferred until a real machine or accountable tester is available.

## 12. Risk register

| Risk | Effect | Mitigation |
| --- | --- | --- |
| Broad UI refactor during release | Regressions and delayed delivery | Limit v1.2 to Home targeting and release defects |
| Same-window Quick Panel limitations | Geometry/focus surprises | Stabilize current behavior; continue redesign separately |
| Only one local bulb | Partial selection lacks physical proof | Use deterministic multi-device fakes; seek later tester smoke |
| GitHub/network unavailable | Slow or blocked startup | Bounded, optional, failure-safe update check |
| Configuration bundled or overwritten | User data loss | Use Flet user storage and test replacement explicitly |
| RGBIC prerelease leaks into stable | Unsafe experimental exposure | Separate branch, prerelease flag and stable channel filter |
| Transport success treated as visual success | False validation | Require independent tester observation in every fixture |
| Linux behavior inferred from CI | Unsupported desktop claim | Require GNOME/Wayland/X11 VM evidence before beta packaging |

## 13. Checkpoint discipline

For every implementation block:

1. begin from a clean worktree;
2. identify the exact files and protected boundaries;
3. add or update focused tests;
4. run focused tests before the full suite;
5. run compile, i18n and `git diff --check` as applicable;
6. perform the required manual smoke before claiming completion;
7. inspect `git status` and `git diff --stat`;
8. create one descriptive commit;
9. push the checkpoint so notebook and PC stay synchronized;
10. record final evidence in a query when the phase closes.

Never stage real files from `config/json`, logs, tester fixtures containing
identifiers, `.venv`, `build` or `dist` without inspecting them explicitly.
